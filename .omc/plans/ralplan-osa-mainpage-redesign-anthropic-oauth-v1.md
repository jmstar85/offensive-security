## 2. RALPLAN-DR Summary

### Principles (governing constraints, in priority order)
1. **Additive, reversible, flag-gated — with one non-reversible caveat made explicit.** C3 never removes or alters the working API-key path: the live resolver query for the user's own credential row (`credential_resolver.py:39-58`, returning a plaintext `str`) and the `anthropic_provider.py:11-12` api_key ctor are untouched. The subscription-OAuth path ships behind a reversible config flag so the *code* can be disabled in one setting change if Anthropic breaks it. **True fallback (stated precisely — do NOT rely on a dead branch):** when the flag is off, an OAuth-only user with no api_key row does NOT silently borrow an org key. The `settings.anthropic_api_key` org-key fallback at `credential_resolver.py:60-63` is guarded by `if not settings.osa_multi_provider_llm` (`:61`) and `osa_multi_provider_llm` defaults to **True** (`config.py:202`) in the deployed config, so that branch is **INERT in production** — do not cite it as the safety net. The real reversibility guarantee is: (i) a user who has their OWN api_key credential row keeps running unchanged (that row resolves at `:39-58` before any fallback), and (ii) an OAuth-only user with no api_key row gets a clean `CredentialNotFound` (`:64-67`) — the session fails cleanly and the user adds a key. That clean-failure behavior is acceptable and is the actual guarantee; the org-key fallback is not part of it. **Caveat (must be stated, not implied):** the flag reverts the code but CANNOT revert Anthropic banning the user's real Pro/Max account for a ToS violation. That blast radius is outside the flag. The flag contains code reversibility, not account reversibility (see ADR Consequences).
2. **Complete the existing scaffolding; do not rebuild — and do not break existing callers while completing it.** `UserLLMCredential` already models `credential_type='oauth_token'` (`models/credential.py:23-28`); PKCE `oauth_start`/`oauth_callback` already exist (`credentials.py:284-434`). Finish these rather than introduce a parallel system. Completing scaffolding must NOT regress an existing consumer: `resolve_provider_credential` has TWO live callers (`router.py:64` and `copilot_models.py:54`), so any signature evolution is done additively (new sibling helper), never by breaking the existing `-> str` contract (see C3.5). **Second, sharper collision — the `oauth_token` credential_type is NOT anthropic-exclusive.** GitHub Copilot's device flow ALSO stores `credential_type='oauth_token'` (`credentials.py:553-560`) but with a **RAW GitHub token** (no `expires_at`, no JSON blob), and Copilot pentest SESSIONS resolve through the SAME generic path (`llm_provider.py:192` → `LLMRouter().route(db, provider='copilot')` → `router.py:61-65` → `get_client('copilot', token)` → `CopilotProvider(api_key=token)`). Therefore the A1 JSON-blob-parse + Claude-token-refresh logic must be gated on **`provider=='anthropic'`**, NOT on `credential_type=='oauth_token'` alone — otherwise resolving a Copilot session would `json.loads()` a raw `gho_`/`ghu_` token (JSONDecodeError → session crash) and/or fire the Claude refresh against a GitHub refresh token. "Do not break an existing consumer" applies at the session-routing layer, not only the model-listing layer (see C3.5/C3.7).
3. **Left panel + product identity are frozen.** Only the right `<aside>` changes (C1); only the *icon* changes, never the name "OSA Platform" or the `osa-theme`/storage keys (C2, per `index.html:13`).
4. **Self-contained assets only.** The hero (C1) and favicon (C2) are SVG/CSS with no external GIF/video/binary dependency and no CSP/network fetch.
5. **Security-first for secrets; never leak a secret cross-host.** OAuth tokens are Fernet-encrypted at rest (`core/security.encrypt_credential`), never returned in any API response (`credentials.py:3-8` invariant, `_build_credential_response` returns metadata only), never logged. **AND** the org machine key (`ANTHROPIC_API_KEY`, injected at `docker-compose.yml:29`) must NEVER be attached as `X-Api-Key` to requests bound for `claude.ai` — the OAuth-mode client force-omits `X-Api-Key` (see C3.6 / AC3.4). A subscription request that also carries the org key both leaks that key cross-host and silently authenticates on the wrong subscription.

### Decision Drivers (top 3)
1. **Will the token actually drive the Messages API — including the Claude-Code identity the endpoint enforces?** The hardest, ToS-grayest part is not the auth UI but *calling* Claude with a subscription bearer token (`anthropic_provider.py` is api_key-only today). Bearer + `anthropic-beta: oauth-2025-04-20` alone are almost certainly **insufficient**: the subscription-OAuth Messages endpoint enforces a Claude-Code *system-prompt identity* on every turn, yet the pentest orchestrator supplies its own non-Claude-Code `system` prompt (`anthropic_provider.py:27-28` forwards it). If the identity requirement cannot be satisfied without corrupting the pentest system prompt, AC3.5 is structurally unmeetable and C3 must degrade to Option C. This is the make-or-break driver and is now gated at build time (see Build-Time Gate G0).
2. **Redirect-URI compatibility with a reused public client_id.** A reused Claude-Code client_id only permits redirect URIs it was registered with (loopback and/or OOB manual paste). The current server uses a fixed `settings.oauth_redirect_uri` (`credentials.py:307,349`) that will not match — this dictates the flow shape.
3. **Reversibility under vendor instability.** Anthropic can rotate the client_id, revoke the beta header, or block the flow at any time. The design must degrade gracefully back to API-key auth without a redeploy.

### Viable Options — C3 flow shape (the major decision; ≥2 required)

| Option | Description | Pros | Cons |
|---|---|---|---|
| **A — Reuse Claude-Code public client_id + loopback/OOB PKCE** *(RECOMMENDED, contingent on Build-Time Gate G0)* | Point the existing PKCE endpoints at `claude.ai/oauth/authorize` + the Claude token endpoint, using the public Claude-Code `client_id`, S256 PKCE (already at `credentials.py:294-316`), and a redirect the client_id permits: loopback (`http://localhost:PORT/callback`) or OOB manual-paste. Store `oauth_token` + refresh; `AnthropicProvider` sends `Authorization: Bearer` + `anthropic-beta: oauth-2025-04-20`, **force-omits `X-Api-Key`**, and **prepends the Claude-Code identity system block** before the pentest system prompt. | Maximal reuse of existing `oauth_start`/`oauth_callback` (`:284-434`) and `UserLLMCredential`; matches the "Claude-Code-style PKCE" the user asked for; no client-secret custody. | Depends on undocumented internals (public client_id, beta header, **and the Claude-Code identity/system-prompt the Messages endpoint enforces**) that can rotate without notice; redirect-URI must be OOB/loopback (existing fixed `oauth_redirect_uri` needs replacing); refresh-token storage needs a home (schema gap — see below); the anthropic SDK will silently attach the org `ANTHROPIC_API_KEY` as `X-Api-Key` unless explicitly force-omitted (see C3.6). Whole path is contingent on Gate G0 passing — if it fails, A is not shippable and C3 falls back to Option C. |
| **B — Device-flow style, mirroring Copilot** | Reuse the Copilot device-flow pattern (`credentials.py:442-585`, `CopilotConnectModal.tsx`) — poll-based, no redirect URI at all. | No redirect-URI compatibility problem; a proven in-repo pattern (device flow already ships and passes tests); best UX for headless/remote deployments. | Anthropic's subscription OAuth is **not** a device-flow provider — there is no documented `claude.ai` device-code endpoint. Building this means inventing an endpoint that does not exist → **not viable** for the real subscription flow. Retained only as the fallback UX shape *if* Anthropic ever ships device flow. |
| **C — Keep API-key only (status quo)** | Do not implement subscription OAuth; document the API-key path as the supported one. | Zero ToS/stability risk; nothing to maintain. | Fails the explicit user goal ("run sessions on the subscription with no API key"). **Rejected** — but retained as the *runtime fallback* that C3's feature flag falls back to. |

**Invalidation rationale:** Option B is invalidated as the *primary* mechanism because the subscription OAuth surface is an authorization-code + PKCE flow, not a device-code flow — there is no `claude.ai` device endpoint to poll, so B would require fabricating a non-existent endpoint. Option C is invalidated as a *deliverable* because it does not meet the end-to-end goal, but it is deliberately preserved as the **fail-safe the C3 flag reverts to AND as the mandatory fallback if Build-Time Gate G0 fails**. Therefore **Option A is the sole viable primary path *contingent on Gate G0***, with C as its always-present safety net.

### Build-Time Gate G0 — the hard gate that forces Option C (answers the steelman-antithesis)

Option A's entire value rests on impersonating Claude Code to Anthropic's private inference endpoint — not merely via an undocumented `client_id` + `anthropic-beta: oauth-2025-04-20` header, but almost certainly ALSO via the Claude-Code *system-prompt identity* the endpoint enforces on every turn. Before ANY C3 frontend/UI work (C3.8/C3.9) ships enabled, the following two facts MUST be proven at build time. If either cannot be proven, C3 degrades to Option C: the "Sign in with Claude" button is **not shipped enabled** (flag stays `False`, button hidden), the API-key path is documented as the supported path, and AC3.5 is explicitly recorded as unmet-by-design rather than shipped as a green-looking-but-false criterion.

- **G0.a — Identity requirement is satisfiable WITHOUT corrupting the pentest system prompt.** Prove that OAuth mode can present the Claude-Code identity (as an additional leading `system` block — see C3.6b) AND still deliver the orchestrator's own pentest `system` prompt, and that a real turn (real pentest system prompt, not a trivial ping) returns 200 rather than 401/403. If the endpoint only accepts a pure Claude-Code system prompt (i.e., the pentest prompt cannot coexist), G0 FAILS → Option C.
- **G0.b — `X-Api-Key` is provably absent from the BUILT request headers even with `ANTHROPIC_API_KEY` set in env.** Prove, by asserting on the SDK's **built request headers** — `client._build_headers(FinalRequestOptions.construct(method="post", url="/v1/messages", json_data={...}))` (or a captured `httpx.Request` via a mock transport) — NOT on `client.auth_headers`, that an OAuth-mode `AnthropicProvider` sends `Authorization` only and NEVER `X-Api-Key`, with `ANTHROPIC_API_KEY` present in the process env (as it is in the deployed backend, `docker-compose.yml:29`). **Why the target matters (verified against installed anthropic 0.94.0):** `auth_headers` (`_client.py:397-398`) returns `{**_api_key_auth, **_bearer_auth}` and NEVER consults `_custom_headers`; `_api_key_auth` (`:401-405`) re-emits `{"X-Api-Key": <env key>}` whenever `self.api_key is not None`, and `__init__` (`:332-334`) sets `self.api_key = os.environ.get("ANTHROPIC_API_KEY")` when `api_key=None`. The `X-Api-Key: Omit()` we pass in `default_headers` lands in `_custom_headers` (`_base_client.py:685-693`) and is only stripped by `_merge_mappings` (`:2262-2272`) inside `_build_headers` (`:440`). So `auth_headers` shows `X-Api-Key` PRESENT whether or not the fix is applied — it cannot distinguish fixed-from-unfixed — whereas `_build_headers(...)` shows `X-Api-Key` ABSENT with the fix and PRESENT without it. Asserting on `auth_headers` would either spuriously FAIL the gate (needlessly forcing Option C) or greenwash a shipped leak. If X-Api-Key cannot be force-omitted from the built headers, G0 FAILS → Option C (shipping would leak the org key cross-host and silently authenticate on the wrong subscription).

The disciplined position, per the antithesis: "cannot verify the identity/system-prompt requirement AND prove `x-api-key` is absent at build time" is a HARD gate that forces Option C — it is NOT acceptable to encode "one real subscription turn" as an acceptance criterion that may be structurally unmeetable without deeper spoofing. Marginal user value (no-API-key convenience) is small; the risks (non-flag-revertible account ban + silent-wrong-subscription trap) are large, so the gate is mandatory, not advisory.

### Sub-decision — refresh-token & second-secret storage (schema gap)
`UserLLMCredential` (`models/credential.py:11-32`) has **one** secret column (`encrypted_value`) and **no** `refresh_token` column. The subscription flow returns both an access token and a refresh token. Two viable options:
- **A1 (RECOMMENDED)** — Store a Fernet-encrypted JSON blob `{"access_token","refresh_token","token_type"}` in the existing `encrypted_value` column for the **anthropic** subscription credential; keep `expires_at` as-is. No migration; fully additive. **Read-path call-out (do not skip) — branch on PROVIDER, not `credential_type`:** `credential_resolver.py:52` currently returns `decrypt_credential(row.encrypted_value)` as a *plaintext string* — that is exactly what api_key AND Copilot `oauth_token` rows expect (Copilot stores a RAW GitHub token under `credential_type='oauth_token'`, `credentials.py:553-560`). Under A1 only the **anthropic** `oauth_token` row holds a JSON blob. So the read path must branch on **`provider=='anthropic'`**: for an anthropic `oauth_token` row it JSON-parses the blob and selects `access_token` (after any refresh); for **every other row — including a Copilot `oauth_token` row — it returns the plaintext string unchanged** (no `json.loads`, no refresh). Branching on `credential_type=='oauth_token'` alone would crash a Copilot session (`json.loads('gho_...')` → JSONDecodeError). This branch lives in the new additive typed helper (C3.5), NOT in the existing `-> str` function, so the api_key/copilot read path is byte-identical.
- **A2** — Add a nullable `encrypted_refresh_token` column via a new additive migration (`013_oauth_refresh`). Cleaner schema, but requires a migration + model change and touches the resolver read path.

Recommend **A1** for reversibility (no schema change to unwind) unless the critic prefers explicit columns. **This A1-vs-A2 sub-decision is resolved to A1 here (not deferred to the critic)**; A2 remains documented as the reversible upgrade path if explicit columns are later preferred.

## 3. Pre-Mortem — 5 Failure Scenarios

**Scenario 1 — Anthropic rotates the client_id or revokes the `anthropic-beta: oauth-*` header.**
*Symptom:* authorize returns `invalid_client`, or Messages API returns 401 `authentication_error` on a previously-working token.
*Blast radius:* every subscription-OAuth session fails; API-key sessions are unaffected.
*Mitigation:* (a) the reversible feature flag (`osa_claude_subscription_oauth`) disables the button and the resolver branch in one setting; (b) a user who has their OWN api_key credential row keeps running unchanged — that row resolves at `credential_resolver.py:39-58` before any fallback and is completely untouched by C3; an OAuth-only user with no api_key row gets a clean `CredentialNotFound` (`:64-67`) and adds a key. **Do NOT cite the `settings.anthropic_api_key` org-key fallback (`:60-63`) as the safety net — it is guarded by `if not settings.osa_multi_provider_llm` (`:61`) and `osa_multi_provider_llm` defaults to True (`config.py:202`), so it is INERT in the deployed config.** (c) `client_id`, authorize URL, token URL, and beta-header string are **config values**, not literals, so a rotation is a config edit, not a code change. Add a startup log line asserting the flag state.

**Scenario 2 — Silent cross-subscription org-key leak: the request runs on the org's `ANTHROPIC_API_KEY`, not the user's subscription, while the probe goes green.**
*Symptom:* token exchange succeeds and stores an `oauth_token` credential; the live probe returns 200; the team believes sessions run on the user's subscription — but requests to `claude.ai` also carry `X-Api-Key: <org key>` and may authenticate/bill against that org machine key, so AC3.5's "runs on the user's subscription" is FALSE even though everything looks green.
*Root cause (verified against the installed anthropic SDK 0.94.0, `anthropic/_version.py`; pin `anthropic>=0.40.0` at `backend/pyproject.toml:19`):* the SDK's `auth_headers` property (`_client.py:397-398`, `AsyncAnthropic`) returns `{**_api_key_auth, **_bearer_auth}` — BOTH merged. `_api_key_auth` (`:401-405`) emits `{"X-Api-Key": api_key}` whenever `self.api_key is not None`, and `__init__` (`:332-334`) sets `self.api_key = os.environ.get("ANTHROPIC_API_KEY")` when `api_key` is None. The deployed backend injects `ANTHROPIC_API_KEY` (`docker-compose.yml:29`), so constructing `AsyncAnthropic(auth_token=token)` alone attaches BOTH the org key (`X-Api-Key`) AND the subscription bearer. Passing `api_key=None` does NOT fix it — the env is re-read. (The earlier claim that "the SDK omits x-api-key when constructed with `auth_token=`" was FACTUALLY WRONG and is retracted.)
*Blast radius:* org secret leaked cross-host to `claude.ai`; wrong-subscription billing; AC3.5 false while the probe passes — a silent-wrong-subscription trap.
*Mitigation:* force-omit via `default_headers={"X-Api-Key": anthropic.Omit()}`. **Exact mechanism (verified against installed anthropic 0.94.0):** the Omit sentinel lands in `_custom_headers` (set at `_base_client.py:393`), which is merged LAST in the `default_headers` property (`_base_client.py:685-693`, order: `platform_headers` → `auth_headers` → `_custom_headers`), so it overrides the `X-Api-Key` that `auth_headers` emits from the env key. `_merge_mappings` (`_base_client.py:2262-2272`) then STRIPS every `Omit`-valued entry when `_build_headers` (`:440-451`) assembles the request, so `X-Api-Key` is ABSENT from the built headers while `Authorization: Bearer` remains. The Anthropic `_validate_headers` override (`_client.py:425-437`) then passes at its very first check (`:426` `if headers.get("Authorization") or headers.get("X-Api-Key")` → Authorization present → return); its Omit-tolerant branch (`:430` `isinstance(custom_headers.get("X-Api-Key"), Omit)`) is a *secondary* path not even exercised here, and the base `_validate_headers` (`_base_client.py:701`) does nothing. **The Omit is thus a `_merge_mappings`/`default_headers` effect — it NEVER touches `auth_headers`.** Therefore the §4 unit test MUST assert on the **built request headers** — `client._build_headers(FinalRequestOptions.construct(method="post", url="/v1/messages", json_data={...}))` (or a captured `httpx.Request` via a mock transport) — NOT on `auth_headers` (which shows `X-Api-Key` present in BOTH the fixed and unfixed case and so cannot discriminate) and NOT on constructor kwargs. Assert that `Authorization` is present and `X-Api-Key` is absent on the built headers, **with `ANTHROPIC_API_KEY` set in the process env**. This is Gate G0.b. Additionally gate acceptance on a live inference probe (Scenario 4 covers the identity dimension) rather than on token storage.

**Scenario 3 — Favicon/theme/hero changes break the Vite dist build or the PWA.**
*Symptom:* `manifest.webmanifest` icon mismatch → PWA install fails or shows a blank icon; `dist/index.html` (the built mirror, `frontend/dist/index.html`) goes stale vs `index.html`; a heavy inline SVG animation regresses Lighthouse/CLS; light-theme hero unreadable.
*Blast radius:* auth pages render wrong, or install/tab icon is broken for all users.
*Mitigation:* rebuild `dist` from source (never hand-edit both); verify the favicon at **16px** before propagation; run `tsc --noEmit` + `vite build`; visually verify both light and dark themes; keep the hero animation GPU-cheap (transform/opacity only, `prefers-reduced-motion` honored) and confirm the right panel stays `hidden lg:flex` (`Login.tsx:163`) so mobile CLS is unchanged.

**Scenario 4 — OAuth token authenticates but the Messages endpoint rejects the pentest system prompt because the Claude-Code identity is missing (the MOST PROBABLE real failure).**
*Symptom:* token exchange and storage succeed; a trivial ping might even pass; but the first REAL pentest turn — which forwards the orchestrator's own non-Claude-Code `system` prompt (`anthropic_provider.py:27-28`) — returns 401/403 from `messages.create`. Bearer + `anthropic-beta: oauth-2025-04-20` alone are insufficient for this flow; the subscription-OAuth endpoint enforces a Claude-Code system-prompt identity.
*Blast radius:* AC3.5 (a real pentest turn on the subscription) fails in production while a trivial storage/ping test looked green — the acceptance criterion is structurally unmeetable unless the identity is encoded.
*Mitigation:* (a) OAuth mode PREPENDS the Claude-Code identity as a leading `system` block, then appends the orchestrator's pentest system prompt as a subsequent block (C3.6b) — verified at build time (Gate G0.a); (b) the C3.10 live probe uses the REAL pentest system prompt, not a trivial ping, so it fails exactly when real sessions would; (c) if identity and the pentest prompt cannot coexist, Gate G0.a FAILS and C3 degrades to Option C rather than shipping an unmeetable AC3.5; (d) test the degrade path itself — add a G0.a companion assertion that when the endpoint rejects a two-block `system` list the provider surfaces the Option-C degrade signal (so Scenario 4's fallback is exercised, not only reasoned about).

**Scenario 5 — Copilot session crash: the A1 typed resolver `json.loads()` a raw GitHub token because the `oauth_token` blob-parse was gated on `credential_type` instead of `provider` (the MOST PROBABLE regression in a SHIPPED feature).**
*Symptom:* a user with a working GitHub Copilot connection starts a Copilot pentest session; `LLMRouter().route(db, provider='copilot')` resolves the credential; if the typed helper (C3.5) blob-parses every `oauth_token` row, it calls `json.loads('gho_...')` on the raw GitHub token → `JSONDecodeError` (or fires the Claude token-refresh against a GitHub refresh token) → the session crashes at role-client mint (`llm_provider.py:192`). The model-listing caller (`copilot_models.py:54`) would NOT catch this because it still uses the untouched `resolve_provider_credential(-> str)` — the break is confined to the session-routing path, exactly where no v1–v3 test looked.
*Root cause:* Copilot device flow stores `credential_type='oauth_token'` with a RAW GitHub token (`credentials.py:553-560`, no `expires_at`, no JSON blob), and Copilot sessions share the generic `route()` path (`router.py:61-65`). Branching the A1 JSON-blob-parse + Claude-refresh on `credential_type=='oauth_token'` alone (rather than `provider=='anthropic'`) sweeps the Copilot token into the anthropic decode path.
*Blast radius:* every Copilot pentest session fails once C3 ships; a currently-passing shipped feature regresses; anthropic and api_key sessions are unaffected.
*Mitigation:* (a) gate the blob-parse + refresh strictly on `provider=='anthropic'` inside the typed helper (C3.5); (b) route() calls the typed helper ONLY for anthropic and keeps `resolve_provider_credential(-> str)` for copilot/openai/google (C3.7) — belt-and-suspenders so even a mis-call cannot crash; (c) a regression test asserts `route(provider='copilot')` with an `oauth_token` row yields the RAW GitHub token and constructs a `CopilotProvider`/starts a session (§4 C3 integration-regression); (d) the typed-helper contract test asserts a Copilot `oauth_token` row is returned as a RAW string, NOT json-parsed (§4 C3 unit item d).

## 9. ADR — Architecture Decision Record

**Decision.** Implement C3 as **Option A, contingent on Build-Time Gate G0**: complete the existing PKCE endpoints to run the **Claude-Code-style subscription OAuth** against `claude.ai` using a reused public client_id + `anthropic-beta: oauth-2025-04-20`, storing an `oauth_token` `UserLLMCredential` (access+refresh as a Fernet JSON blob — sub-decision A1, resolved), and teaching `AnthropicProvider` in OAuth mode to send `Authorization: Bearer`, **force-omit `X-Api-Key`** (`default_headers={"X-Api-Key": anthropic.Omit()}`, because the SDK otherwise re-reads `ANTHROPIC_API_KEY` from env and attaches it), and **prepend the Claude-Code identity system block** ahead of the pentest system prompt. The resolver change is ADDITIVE (new `resolve_provider_credential_typed`; the existing `-> str` function and its `copilot_models.py:54` caller are untouched). The whole path is gated behind a reversible `osa_claude_subscription_oauth` flag that falls back to the untouched API-key path. If Gate G0 (identity satisfiable AND X-Api-Key provably absent) fails, C3 degrades to Option C (button hidden, AC3.5 unmet-by-design). C1 and C2 are self-contained SVG/CSS front-end changes with the product name and left login panel frozen.

**Drivers.** (1) End-to-end inference on the subscription is the real goal, not just an auth UI — and it requires the Claude-Code identity system prompt the endpoint enforces, not just the bearer + beta header. (2) A reused public client_id constrains the redirect to loopback/OOB. (3) The design must degrade to API-key auth under vendor instability without a redeploy.

**Alternatives considered.** *Option B (device flow like Copilot)* — invalidated because Anthropic's subscription OAuth is authorization-code + PKCE, not device-code; there is no `claude.ai` device endpoint to poll. *Option C (API-key only)* — invalidated as a deliverable (fails the goal) but retained BOTH as the runtime fallback the flag reverts to AND as the mandatory fallback if Build-Time Gate G0 fails (identity unsatisfiable or X-Api-Key un-omittable). *Sub-decision A2 (new refresh-token column)* — viable but rejected as default in favor of A1 (no migration, easier to unwind).

**Why chosen.** Option A maximizes reuse of shipped scaffolding (`credentials.py:284-434`, `UserLLMCredential`), directly matches the user's stated "Claude-Code-style PKCE" intent, needs no client-secret custody, and — combined with the flag plus the untouched user-owned-api_key-credential fallback (`credential_resolver.py:39-58`, else clean `CredentialNotFound`; the org-key branch `:60-63` is inert and not relied upon) — satisfies the reversibility principle demanded by the HIGH ToS/stability risk.

**Consequences.** (+) Additive, flag-gated; existing api-key auth and the `resolve_provider_credential(-> str)`/copilot-model-listing path untouched, and the Copilot pentest-SESSION path (`route(provider='copilot')`) stays byte-identical because the A1 blob-parse/refresh is gated on `provider=='anthropic'` and the router routes only anthropic through the typed helper (Scenario 5 guard). The reversibility fallback is the user's OWN api_key credential row (`credential_resolver.py:39-58`), else a clean `CredentialNotFound` — NOT the inert org-key branch (`:60-63`, dead under `osa_multi_provider_llm=True`). (+) A single config surface (client_id/URLs/scopes/beta-header/identity-prompt) absorbs vendor rotations without code changes. (+) X-Api-Key force-omit (verified on the SDK's **built request headers** — `_build_headers(...)` / a captured `httpx.Request`, NOT `auth_headers` where the Omit is invisible — with env set, plus a wire-level integration assertion and an SDK-upgrade contract test) closes the cross-host org-key leak. (−) **The flag's reversibility is CODE-ONLY and does NOT contain the full blast radius:** if Anthropic bans the user's real Pro/Max account for the ToS violation (impersonating the official CLI + automated offensive-security use on a consumer subscription), flipping `osa_claude_subscription_oauth=false` reverts the code but CANNOT un-ban the account — that consequence is non-reversible and explicitly accepted by the user. (−) Depends on undocumented, rotatable Anthropic internals (client_id, beta header, AND the enforced Claude-Code identity system prompt) — may break without notice. (−) Storing two secrets in one column (A1) is slightly less clean than explicit columns. (−) Requires a live-inference gate (with the real pentest system prompt) for acceptance, which cannot fully run in headless CI (marked `@pytest.mark.live`). (−) Marginal user value (no-API-key convenience) is small relative to these risks, which is why Gate G0 can force Option C.

**Follow-ups.** (1) Confirm the exact client_id / authorize-URL / token-URL / scopes / audience AND the Claude-Code identity system-prompt string at build time (Gate G0) and record them in config with a "vendor-rotatable" comment. (2) A1-vs-A2 is **resolved to A1** (Fernet JSON blob; read-path branch lives in `resolve_provider_credential_typed`, not the `-> str` function); A2 remains the documented reversible upgrade if explicit columns are later preferred. (3) Add an ops runbook entry: "if subscription OAuth 401s, flip `osa_claude_subscription_oauth=false`; note this reverts code only, not any account action Anthropic may have taken." (4) Track any Anthropic move toward an official third-party OAuth program to replace this path. (5) Tighten the `anthropic` pin beyond `>=0.40.0` to a compatible-release bound (or keep the SDK-upgrade contract test green) so a future bump cannot silently reopen the cross-host leak through changed `_build_headers`/`_merge_mappings` internals. (6) The `oauth_token` credential_type is shared by anthropic (JSON blob) and Copilot (raw token); keep the A1 blob-parse/refresh strictly `provider`-gated. If a THIRD provider ever adopts `oauth_token`, add its own provider gate + a `route(provider=X)` regression test before shipping — never widen the anthropic decode branch to `credential_type` alone. (7) See open questions in `.omc/plans/open-questions.md`.
