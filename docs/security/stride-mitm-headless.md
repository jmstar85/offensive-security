# STRIDE Deep Dive — Surface 2: MITM Proxy + Headless Sidecars

> **Surface:** mitmproxy sidecar + `MitmProxyAdapter` + headless browser container
> **Threat model version:** 2.0
> **Wave coverage:** W4 (PR4.1)
> **Environment variable:** `OSA_TRAFFIC_VIA_MITM`
> **Last updated:** 2026-06-01

---

## Overview

The MITM proxy sidecar (mitmproxy) and headless browser container are launched on `osa-net` to
intercept and record HTTP/HTTPS traffic generated by attack agents. The `MitmProxyAdapter` in the
backend connects to the sidecar, retrieves captured flows, and forwards them through the scrubber
pipeline. The headless browser runs in a non-privileged container and is controlled by attack agents
via the backend.

---

## Spoofing

### Threat S-1: Rogue sidecar impersonates legitimate mitmproxy instance
- **Scenario:** An attacker who has gained access to `osa-net` starts a fake mitmproxy container
  that returns crafted capture events to the backend adapter.
- **Likelihood:** Low — access to `osa-net` requires container-level compromise.
- **Impact:** High — fake captures could inject false findings or suppress real ones.
- **Existing v2.0 mitigation:** Sidecar started with pinned image digest in compose file; digest
  verified at container startup by `MitmProxyAdapter`; port binding restricted to `osa-net` CIDR;
  sidecar registers with backend on startup using a shared secret.
  Proved by: `backend/tests/e2e/test_attack_matrix.py` — MITM adapter integration tests (PR4.1).
- **Residual risk:** Low. Pinned digest prevents substitution; shared secret prevents registration
  of a rogue sidecar.
- **Owner:** Infra team

### Threat S-2: Forged MITM capture events injected into adapter
- **Scenario:** A compromised container on `osa-net` sends crafted JSON payloads to the MITM
  adapter endpoint, injecting false capture records.
- **Likelihood:** Low-Medium.
- **Impact:** Medium — false findings could misdirect attack agents.
- **Existing v2.0 mitigation:** Capture event schema validated with strict JSON schema; unexpected
  fields rejected; source container IP verified against known sidecar IP on `osa-net`; events signed
  with sidecar HMAC key.
- **Residual risk:** Low.
- **Owner:** Backend team

## Tampering

### Threat T-1: Attacker modifies intercepted traffic before backend sees it
- **Scenario:** A container on `osa-net` performs a man-in-the-middle of the MITM sidecar → backend
  communication path, modifying captured flows to hide attack traffic or inject false evidence.
- **Likelihood:** Very Low — requires double MITM on internal network.
- **Impact:** High — tampered evidence undermines attack finding validity.
- **Existing v2.0 mitigation:** MITM captures are read-only in adapter (no write-back path);
  captures signed with sidecar HMAC before transmission; backend re-verifies HMAC on receipt;
  unexpected HMAC failure triggers P1 alert and session abort.
- **Residual risk:** Low.
- **Owner:** Backend team

### Threat T-2: `OSA_TRAFFIC_VIA_MITM=0` bypass via environment variable injection
- **Scenario:** Attacker injects an environment variable override at container runtime to disable
  MITM routing, preventing traffic capture from occurring.
- **Likelihood:** Very Low — env var injection at container runtime requires host-level access.
- **Impact:** Medium — MITM disabled silently; attack traffic not captured.
- **Existing v2.0 mitigation:** `OSA_TRAFFIC_VIA_MITM` set at container launch from compose/helm
  values; no runtime mutation path is exposed; value logged at startup and audited.
- **Residual risk:** Low.
- **Owner:** Infra team

## Repudiation

### Threat R-1: MITM captures not persisted, making forensics impossible
- **Scenario:** MITM captures are held only in memory; container crash or restart destroys all
  capture evidence before it is reviewed.
- **Likelihood:** Medium — container restarts are routine.
- **Impact:** High — loss of attack traffic evidence.
- **Existing v2.0 mitigation:** Capture store persisted to named Docker volume mounted into sidecar;
  retention policy (7 days) enforced by volume cleanup job; audit event emitted on capture start
  and stop with session reference.
- **Residual risk:** Low-Medium. Volume loss (host disk failure) would destroy captures.
  Backup of capture volume recommended for high-value sessions.
- **Owner:** Platform team

### Threat R-2: Headless browser actions not attributable to a session
- **Scenario:** Headless browser performs actions (e.g., form submissions) that are not logged
  with their originating session ID, preventing attribution in an incident.
- **Likelihood:** Medium.
- **Impact:** Medium.
- **Existing v2.0 mitigation:** Every headless browser command tagged with session ID at the
  adapter layer; command log written to session audit store before execution.
- **Residual risk:** Low.
- **Owner:** Backend team

## Information Disclosure

### Threat I-1: MITM captures contain credentials or PII from target responses
- **Scenario:** Target site returns session cookies, API keys, or PII in HTTP responses that are
  captured by mitmproxy and stored without redaction.
- **Likelihood:** High — attack targets by definition may return sensitive data.
- **Impact:** High — credential/PII exposure in capture store.
- **Existing v2.0 mitigation:** Scrubber pipeline (all 4 layers) applied to all captured content
  before storage; raw captures never returned to operators (only scrubbed versions); TEAM_ADMIN
  gate required to access raw capture data.
  Proved by: `backend/tests/safety/test_adversarial_prompts.py` — scrubber coverage on MITM content.
- **Residual risk:** Medium. Novel credential formats not covered by Layer 1 regex may pass through.
  Quarterly scrubber corpus refresh is the control.
- **Owner:** ML team

### Threat I-2: Headless browser leaks internal URL structure via error messages
- **Scenario:** Headless browser navigation errors expose internal redirect URLs or API endpoint
  patterns in error responses returned to operators.
- **Likelihood:** Low.
- **Impact:** Low-Medium.
- **Existing v2.0 mitigation:** Headless error responses sanitised before forwarding; URL patterns
  matched against allowlist; unexpected internal URLs stripped.
- **Residual risk:** Low.
- **Owner:** Backend team

## Denial of Service

### Threat D-1: High-volume target responses flood MITM capture buffer
- **Scenario:** Target returns extremely large or high-frequency HTTP responses that overflow the
  mitmproxy capture buffer, causing memory exhaustion in the sidecar container.
- **Likelihood:** Medium — large file downloads or streaming responses are common.
- **Impact:** Medium — sidecar OOM kill; capture data lost; session disrupted.
- **Existing v2.0 mitigation:** Capture buffer size-limited (default 100 MB per session); overflow
  drops with P2 alert; per-response size limit enforced at proxy level; sidecar resource limits
  set in compose (memory + CPU).
- **Residual risk:** Low-Medium. Very high-frequency small responses could still cause issues;
  rate limiting at the proxy level is the secondary control.
- **Owner:** Infra team

### Threat D-2: Headless browser hangs indefinitely on slow target
- **Scenario:** Target page never fully loads, causing the headless browser to hang and block
  the attack session indefinitely.
- **Likelihood:** Medium.
- **Impact:** Medium — session DoS for one operator.
- **Existing v2.0 mitigation:** Headless browser navigation timeout enforced (default 30 s);
  timeout triggers graceful abort + audit event; coordinator wall-clock cap provides second-layer
  protection.
- **Residual risk:** Low.
- **Owner:** Backend team

## Elevation of Privilege

### Threat E-1: Headless browser escapes sandbox via MITM proxy
- **Scenario:** Exploitable vulnerability in headless browser allows renderer escape; attacker
  attempts to pivot via the MITM proxy to reach internal services.
- **Likelihood:** Low — requires browser renderer 0-day.
- **Impact:** Critical — internal network access.
- **Existing v2.0 mitigation:** Headless runs in non-privileged container (no `--privileged`);
  no host-network access; proxy routing only on `osa-net` which has no route to DB or backend
  internal services; container runs as non-root user.
- **Residual risk:** Medium. Browser renderer 0-days are a known risk class. gVisor evaluation
  in backlog as additional sandbox layer.
- **Owner:** Infra team
